# 云回收 1.0 开发文档

> 本文只讲技术实现、架构选型、部署方式和开发约定。  
> 产品范围和业务规则见：[云回收1.0产品需求文档.md](./云回收1.0产品需求文档.md)

## 1. 技术栈

```text
用户端：微信小程序原生 WXML / WXSS / JS
管理端：Web 静态页面 HTML / CSS / JS
后端：微信云开发 CloudBase 云函数，Node.js
数据库：微信云开发数据库
文件：微信云开发云存储
管理端部署：CloudBase 静态网站托管
```

## 2. 总体架构

```text
微信小程序用户端
  ↓ wx.cloud.callFunction
quickstartFunctions 云函数
  ↓
云数据库 / 云存储
  ↑
Web 管理端
  ↓ CloudBase JS SDK 调云函数
quickstartFunctions 云函数
```

管理端和用户端都不直接读写数据库。所有数据操作都经过云函数。

## 3. 端到端调用链

### 3.1 用户端调用链

```text
用户操作小程序页面
→ miniprogram/utils/cloud.js 统一调用云函数
→ quickstartFunctions/index.js 根据 type 分发
→ recycle/orders.js、address.js、categories.js 处理业务
→ 云数据库 / 云存储
→ 返回页面展示
```

### 3.2 管理端调用链

```text
管理员打开 Web 管理端
→ CloudBase JS SDK 调 quickstartFunctions
→ admin.js 校验 sessionToken
→ 查询或更新订单、品类、配置
→ 返回 Web 页面展示
```

### 3.3 图片上传调用链

```text
用户物品照片：小程序上传到云存储 → fileID 写入 orders.photos
打款截图：管理端上传到云存储 → fileID 写入 orders.transferProofs
展示图片：云函数把 fileID 换成临时访问 URL
```

## 6. 订单状态技术约定

1.0 只保留四个状态。

| 状态值 | 展示文案 | 说明 |
|---|---|---|
| `submitted` | 已提交 | 用户提交后自动生成 |
| `processing` | 处理中 | 管理员接单、联系用户、安排上门、回收中都归到这个状态 |
| `completed` | 已完成 | 已填写最终金额，并上传打款截图 |
| `canceled` | 已取消 | 用户取消或管理员取消 |

需要从旧状态迁移时：

| 旧状态 | 新状态 |
|---|---|
| `submitted` | `submitted` |
| `confirmed` | `processing` |
| `assigned` | `processing` |
| `recycling` | `processing` |
| `completed` | `completed` |
| `canceled` | `canceled` |
| `rejected` | `canceled` |

## 7. 订单字段建议

`orders` 集合建议保留或新增以下字段：

```js
{
  _openid: "用户 openid",
  orderNo: "订单号",
  source: "category | photo",
  summary: "订单摘要",
  items: [],
  photos: [],
  addressSnapshot: {
    contactName: "",
    phone: "",
    region: "",
    detail: ""
  },
  appointDate: "预约日期",
  appointSlot: "预约时间段",
  remark: "用户备注",
  status: "submitted | processing | completed | canceled",
  estimatePrice: null,
  finalWeight: null,
  finalPrice: null,
  recyclerName: "",
  recyclerPhone: "",
  transferProofs: [],
  cancelReason: "",
  adminRemark: "",
  createTime: 0,
  updateTime: 0,
  completedAt: null,
  canceledAt: null
}
```

字段说明：

- `finalPrice`：最终给用户的金额。
- `transferProofs`：打款截图 fileID 数组。
- `cancelReason`：取消原因。
- `adminRemark`：内部备注，用户端不一定展示。

## 8. 完成订单规则

管理端把订单改为 `completed` 时，云函数必须校验：

- `finalPrice` 必填。
- `finalWeight` 或实际数量建议必填。
- `transferProofs` 至少有一张截图。

如果缺少打款截图，云函数返回错误，不允许完成订单。

建议错误码：

| 错误码 | 含义 |
|---|---|
| `TRANSFER_PROOF_REQUIRED` | 缺少打款截图 |
| `FINAL_PRICE_REQUIRED` | 缺少最终金额 |
| `ORDER_STATUS_INVALID` | 当前状态不允许操作 |

## 9. 打款截图上传

管理端上传打款截图的流程：

```text
管理员选择图片
→ Web 管理端上传到云存储
→ 获得 fileID
→ 调 adminUpdateOrder
→ 把 fileID 写入 orders.transferProofs
→ 状态改为 completed
```

存储路径建议：

```text
transfer-proofs/{orderNo}/{timestamp}-{random}.jpg
```

打款截图附属在订单详情中，用户端和管理端都可以查看。

## 10. 系统配置

最低起收标准由管理端配置，不写死在代码里。

建议新增 `settings` 集合，存一条业务配置：

```js
{
  key: "recycle_rules",
  minWeightKg: 5,
  minCount: 0,
  photoOrderCheckMinQuantity: false,
  updateTime: 0
}
```

字段说明：

- `minWeightKg`：最低起收重量，默认 5kg。
- `minCount`：最低起收件数，默认为 0，是否启用待确认。
- `photoOrderCheckMinQuantity`：拍照提交是否校验最低起收标准，默认不校验。

管理端需要提供配置入口：

- 修改最低起收重量。
- 修改最低起收件数。
- 配置拍照提交是否校验最低起收标准。

## 11. 管理端鉴权

1.0 管理端只做“是否管理员”的判断，不做复杂角色。

推荐继续使用当前方案：

```text
Web 生成登录票据
→ 管理员用微信扫码
→ 小程序确认登录
→ 云函数读取当前 OPENID
→ 查询 admins 白名单
→ 通过后生成管理 session
→ Web 管理端后续接口带 sessionToken
```

`admins` 集合建议字段：

```js
{
  openid: "",
  name: "",
  role: "admin",
  enabled: true,
  createTime: 0
}
```

能登录管理端的人默认都是管理员。

## 12. Web 管理端部署

Web 管理端可以部署到 CloudBase 静态网站托管。

这样项目形态是：

```text
小程序用户端：微信小程序
云函数和数据库：微信云开发 CloudBase
Web 管理端：CloudBase 静态网站托管
```

这不等于传统意义上的同一台服务器，但都在微信云开发体系内，适合当前项目快速上线。

1.0 不单独购买服务器。

当前 Web 管理端正式域名还没处理好，先按开发环境推进。上线前再绑定正式域名或使用 CloudBase 静态网站托管默认域名测试。

## 13. 个人小程序迁移企业小程序

当前个人小程序只能作为开发和测试环境。

迁移企业小程序时需要处理：

- 更换 `project.config.json` 里的正式 AppID。
- 更换小程序端云环境 ID。
- 更换 `admin-web/config.js` 里的云环境 ID。
- 在正式云环境重新部署云函数。
- 在正式云环境初始化数据库集合。
- 重新配置管理员 OpenID 白名单。
- 重新配置腾讯地图 Key 的 AppID 白名单。
- 重新配置隐私协议、定位权限和服务类目。

重要点：

- 不同小程序 AppID 下，同一个微信用户的 OpenID 不同。
- 用户订单、地址、管理员白名单不能直接按旧 OpenID 复用。
- 如果需要保留历史订单，需要单独设计数据迁移方案。

## 15. 开发优先级

建议按下面顺序做：

1. 调整订单状态，只保留四个状态。
2. 调整用户端订单状态展示。
3. 调整管理端订单筛选和状态修改。
4. 增加打款截图上传。
5. 增加完成订单的云函数校验。
6. 调整订单详情展示最终金额和完成记录。
7. 增加最低起收标准配置。
8. 整理企业小程序迁移配置。

## 17. 后续扩展

后续工作人员小程序端上线时，不需要推翻现有架构。

可以新增：

- `workers` 集合。
- `worker_sessions` 集合。
- `workerListOrders` 接口。
- `workerUpdateOrder` 接口。

工作人员端只处理分配给自己的订单，管理端继续保留全量管理能力。
